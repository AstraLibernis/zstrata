The answer first

Which side wins, by kind of work

"Wins from" is the smallest tested size at which the GPU, including sending the data and reading the result back, beats the best of one core and all threads. The resident column is the same with the data already on the GPU.

The layers

Two stacks of memory, one narrow bridge

Each side has its own ladder of storage, from tiny and fast to large and slow. The link between them is slower than either side's main memory, and every trip across has a fixed cost.

  • The CPU waits less; the GPU moves more. A random read from the CPU's L1 takes 1 ns, against 28 ns for the GPU's nearest cache, and RAM answers in 85 ns where VRAM takes 310. But the GPU streams 11× more from VRAM (640 GB/s vs 60) and 7–10× more from its caches.1
  • The X3D cache is the CPU's big asset: 96 MiB at 10–17 ns, more than the GPU's 64 MiB Infinity Cache and about 10× faster to reach.
  • The bridge is the narrowest part. Bulk copies run at 22–28 GB/s, below either side's main memory. One round trip costs 34–37 µs2, which is about 11 million floating-point operations on one CPU core.

Crossovers

Five tasks, three places, every size

Time per run, both axes on log scales; lower is better. gpu-kernel is the GPU's own work, gpu-resident adds the round trip (the data already on the GPU), and gpu-with-transfer is the whole trip a program pays. Every GPU result was checked against the CPU's at every size.

  • map (y = a·x + b): shipping data never pays. Sending 64M floats and fetching the result takes 39 ms, while all CPU threads finish in 11 ms. If the data already lives on the GPU it is 12× faster there (0.9 ms).
  • nets (64-wide networks): uniform and compute-heavy. The GPU wins from 64 networks even with transfers. At 4,096 networks it is 3.6× faster than all CPU threads including transfers, and 30× when the weights already live on the GPU.
  • trees (128 decision trees, depth 8): branchy, with scattered reads. Below 4K rows the GPU is slower than the CPU threads. A lane walking 1,024 dependent nodes waits on memory at every step: 313 µs for 256 rows. At 2M rows it is only 2.5× faster than 16 threads.
  • chains (many 1,000-step sequences): each chain is step by step, but there are many. The GPU wins from 64K chains.
  • chain-long (one sequence): nothing to spread. One CPU core does a step in 1.1 ns, the GPU takes 8–16 ns, and threads cannot help at all.
Inside the CPU

Vectors, independent work, one thread per core

  • AVX-512 is 16× scalar (0.33 vs 0.02 TFLOP/s per core), but only with at least 8 independent chains of work. With one chain each multiply-add waits about 4 cycles for the previous one.
  • Past 28 live vectors the registers run out (AVX-512 has 32) and speed halves. This is the CPU's version of the GPU's register cliff, gentler because the spill goes to L1.
  • SMT adds nothing for arithmetic. 8 threads on 8 cores reach 2.67 TFLOP/s and 16 threads also 2.67. 12 threads are slower (2.0) because 4 cores carry two threads and the rest wait for them.
  • A mispredicted branch costs about 4.4 ns (2.35 ns per item on random data vs 0.19 predictable). Branchless code takes 0.38 ns either way.
  • Handing work to threads: starting a new thread costs 9 µs, and a round trip on a warm pool 0.14–1.0 µs. A pool that has gone to sleep takes 26–30 µs to wake.
  • Freshly allocated memory writes at 4.6 GB/s, and the same memory written again at 10.4. The first touch pays for the operating system to supply each page.
The link

Write straight into VRAM, read back by copy

  • Direct writes into VRAM (resizable BAR) reach 22 GB/s at any size and skip a staging copy. Staged uploads top out at 14 GB/s.
  • Never read VRAM directly from the CPU: 0.07 GB/s, 150× slower than letting the GPU copy into CPU memory (10–13 GB/s).
  • Small transfers are all overhead: 4 KiB staged takes as long as a round trip (about 40 µs).
Inside the GPU

The GPU map, in short

The full GPU map is its own page (first built in an earlier Vulkan lab project, measured again here with the same probes). The points that matter for placement:

  • fp32 peak 50 TFLOP/s with 64-lane subgroups, half that with 32-lane ones. Matrix units: fp16 211, fp8 391, int8 398.
  • 256 registers per lane, then a 25× cliff. A subgroup costs the same however many of its 64 lanes are busy.
  • Networks 64 wide with weights in registers are the best fp32 layout (11.8 TFLOP/s). Pack narrower networks several to a subgroup.
Placement guide

Where to put work and data

Below about 40 µs of CPU work, stay on the CPU. One GPU round trip costs 34–37 µs2 before any work happens.

Move work to the data, not data to the work. The link (22–28 GB/s) is slower than the CPU reading its own RAM (60 GB/s). Simple per-item math on CPU-side data never pays to ship.

Once data is on the GPU, keep it there across steps. The same map is 3.5× slower than the CPU when shipped each time, and 12× faster when resident. Populations, training state and simulations should live in VRAM between generations.

Send the GPU uniform, compute-heavy work on many items: network populations (from 64 networks), many independent simulations (from ~64K). Write inputs straight into VRAM, and read results back by GPU copy, never by reading VRAM from the CPU.

Keep branchy, scattered and sequential work on the CPU: tree models, parsing, decision logic, any single chain of dependent steps. The GPU gains little on branchy work (2.5× over 16 threads at 2M rows) and loses on small batches and single chains.

On the CPU: AVX-512 with 8–28 independent chains, one thread per core, a warm pool, allocate once. That's 16× from vectors and 8× from cores. SMT adds nothing for arithmetic, and a sleeping pool costs 26–30 µs to wake.

Size working sets to a cache level. CPU: 1 MiB per core in L2, up to ~64 MiB in the X3D L3 before RAM latency shows. GPU: 8 MiB in L2, 64 MiB in Infinity Cache, and fit per-lane state under 256 registers.

  • The GPU's caches lead the CPU's by 2–5×, not 7–10×: L2 6.1–8.5 TB/s against the CPU's 1.6–2.3 (all threads), the Infinity Cache 2.3 TB/s against the CPU's L3 0.65–1.0. Each step sits exactly at the published cache size.
  • The CPU clock (new test): 5.02 GHz with one core busy, 4.89 with all 8; it held at 4.96–5.06 GHz through a full run.
  • A GPU round trip costs about 70 µs on Windows2: record 1.9, submit 12.4, launch 41–46, the GPU's own work 0.4, waking the waiting thread 25–28. The first trip after the machine sits idle costs about 250 µs, mostly a slower GPU launch.
  • Batch GPU work: 256 dependent dispatches in one submit cost 0.85 µs each, against 41–48 µs with a submit each.
  • Waiting: polling for 50 µs and then sleeping gives the fastest trip (44 µs) at almost no CPU cost; pure polling burns a core for the whole job.
  • Threads on Windows: starting one costs 92–98 µs (Linux 9), 60 with a 1 MiB stack; a warm pool hands work over in 0.12–0.49 µs. One thread reads L1 at 633 GB/s (generation 1: 334). RAM latency 92 ns. Fresh memory: 11 GB/s first write, 21 rewrite.
  • Every crossover verdict is the same as in generation 1: networks on the GPU from 64, trees from 4K rows, chains from 64K, streaming math only when the data already lives on the GPU, one long chain never. Margins at the largest sizes: networks 4.2× with transfers (46× resident), trees 2.7×, chains 10.8×.
  • Opting out of Windows power throttling changed nothing on this desktop (3 runs each way).
